# 第一次用，先认识项目环境

这个 skill 不知道项目的代码仓库在哪，不知道缺陷系统是什么，不知道运行证据去哪拿。第一次用的时候，先把这几件事问清楚，写进 `project-config.md`。以后每天就不用再问。

不管用户第一条说什么，只要还没有 `project-config.md`，就先走这一步。用户说"帮我看看这个 bug"，也要先配环境。不配环境就分析等于在瞎猜。

## 要问的六件事

1. 代码仓库。主仓库路径，有没有子模块，代码托管在哪。
2. 缺陷系统。是什么系统，地址是什么，每天从哪里拉待分析的单，凭证怎么给。拉单的位置要一个能打开的具体东西，保存的筛选器、搜索链接、列表地址都行，原样记下来，别让 AI 自己编一个。注意，要筛选器或搜索链接，不要给一个看板或 dashboard 页面。dashboard 是展示用的，拉不了单，AI 从上面拿不到结构化的 bug 列表。给错了要让用户知道，请他换一个筛选器或搜索链接。
3. 运行证据。日志、控制台、错误上报、缺陷单附件，通常去哪拿。
4. 业务类型。这是什么项目，Web 前端、移动端、后端服务、嵌入式、游戏引擎，还是别的。业务类型决定分类法和检查顺序，有适配包的按适配包走，没有的先按通用来。
5. 参考资料。有没有 PRD、设计文档、接口文档、架构图，放在哪。这些不是必填，但有的话分析时能少走弯路。没有就让用户知道，AI 只能靠代码和缺陷单推断。
6. 业务模块。项目分几个模块，比如订单、支付、登录。有就让用户给一份列表，没有就让 AI 从单子标题里归纳。冷启动时按模块组织历史单。

## 探测顺序

先从环境里自己找，找不到再问用户。

1. 看当前目录有没有 git 仓库。运行 git remote -v，能看出代码托管和仓库路径。
2. 找项目根目录。找 README、package.json、pyproject.toml、CMakeLists.txt 这类标志文件。
3. 找日志目录。常见的 logs、log、out 目录。
4. 找不齐的部分，一次问完，最多三个问题。别一遍遍问。

## 写配置

把问到的内容写进 `project-config.md`，照着 `config.example.yaml` 的字段填。格式不强求，人看得懂就行，但仓库路径、缺陷系统、每天从哪里拉单、运行证据、业务类型这五样必须有。拉单位置要能打开，保存的筛选器、搜索链接、列表地址都行。参考资料有就写路径，没有写无。

## 验一遍

写完配置后逐个信息源校验，每一步都要实跑，不能假设能用。

1. 打开配置里记下的拉单位置，拉一页单子，看能不能拉到。用 `scripts/adapters/example_api.py` 当样板接项目的缺陷系统，先跑 `--demo` 验证脚本本身。
2. 进主仓库 git pull，看能不能拉到最新。再跑 git log，看有没有近期提交，确认这是一个活的仓库，不是归档的。
3. 找一条旧 bug 的运行证据，看能不能拿到。日志能不能读，附件能不能下。附件下载要单独验，别假设能拉单就能下附件，有些系统看和下走不同接口。
4. 如果有参考资料，打开看一眼能不能读。

每一步验完都要记结果。通了就标通，没通就标没通，写清什么没通。

## 没配全怎么办

验一遍之后，有些信息源可能没通。没通的不等于不能用这个 skill，但要让用户知道后果。

- 缺陷系统拉不到单。不能跑每日循环，但可以单条分析。用户手动把 bug 描述和附件给 AI，AI 照常分析。
- 仓库拉不到最新。可以分析，但查不到最近提交，可能分析到已经被别人修了的问题。
- 运行证据拿不到。可以分析，但结论等级可能上不去，很多 bug 只能标信息不足。
- 附件下不了。可以分析，但看不了截图和录像，显示类和交互类 bug 受影响最大。
- 参考资料没有。可以分析，但理解业务全靠代码和缺陷单，可能漏上下文。

把每项的后果告诉用户，让用户知道现在能做什么、做不到什么。用户决定是先修环境还是带着限制开工。

## 配置里不许写什么

密码、令牌、私钥不许写进 `project-config.md` 正文。用环境变量的方式引用，见 `config.example.yaml` 的 token_env 字段。配置文件可能被分享，凭证不能跟着走。
