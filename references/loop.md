# 每天怎么走

把修 bug 变成每天固定的循环。顺序是，拉单、逐条分析、可选修复提交、写进文件。复盘有昨天留下的分析才做，放在拉单之前。

## 第 0 步，看一眼环境

打开 `project-config.md`，确认三件事。

1. 代码仓库在哪，主仓库和子模块各是什么路径。
2. 缺陷系统在哪，每天从哪里拉单，要一个能打开的具体位置，筛选器或链接。
3. 运行证据去哪拿，是日志、控制台、错误上报，还是缺陷单附件。

没有 `project-config.md` 就先做环境探测（见 `references/bootstrap.md`）。

## 第 1 步，复盘昨天（有昨天的分析才做）

有昨天留下的分析，才做这一步。没有，或者用户只想要新单，直接跳到第 2 步。完整流程看 `references/retrospective.md`。

1. 打开昨天的清单 `bugs_YYYY-MM-DD.md`。
2. 对每条给过结论的 bug，去缺陷系统看别人后来怎么解决的，改了什么，评论说了什么。
3. 对比 skill 上次的结论和别人的解决结论，有差距就写进 `lessons.md` 的偏差表。

昨天没分析，今天就不复盘，不硬凑。

## 第 2 步，拉今天的单

1. 打开配置里记下的拉单位置，把待分析的 bug 拉出来。
2. 去重，以当天日期建一份 `bugs_YYYY-MM-DD.md`。
3. 每条标初始状态，待分析。

## 第 3 步，逐条分析

每一条都要过 `references/depth-gate.md` 和 `references/principles/debugging-principles.md`。

1. 先扫一眼 `lessons.md` 的偏差表，命中的直接按验证路径走，不重新踩坑。
2. 一次只分析一条。同时开好几条，缺陷系统和浏览器容易打架，附件会下不全。
3. 先分类再定位，判断这条属于哪一类（看基本原则）。
4. 按打点表做检查动作，读描述评论、看附件、拿运行证据、搜代码、查最近提交、确认归谁管、复现、确认数据真的到了（拿运行证据的坑看 `references/runtime-evidence.md`）。
5. 给结论，只能三选一，信息不足、无法定论、确定结论。

## 第 4 步，可选，修复和提交

这一步只在用户授权后做，默认只读，给根因和修法，不动代码。授权分级看 `references/autonomy-ladder.md`。

## 第 5 步，写进文件

1. 更新主清单的状态。
2. 生成当天的报告 `bugs_YYYY-MM-DD.md`，带上打点表。
3. 新教训写进 `lessons.md`。
4. 告诉用户成果物在哪。每写一个文件，把它的绝对路径报给用户。至少报三个，当天的 bug 清单、当天的分析报告、经验库。用户不需要自己找文件在哪，AI 写完就主动说。

## 一条 bug 的状态

| 状态 | 意思 | 什么时候 |
|------|------|---------|
| 待分析 | 还没碰 | 拉单后默认 |
| 信息不足 | 关键证据拿不到 | 运行证据缺失、复现不了、上下文不够 |
| 无法定论 | 分析了，但得不出确定结论 | 工序没走完，或者证据不足、证据矛盾 |
| 确定结论 | 证据撑得住，几个证据对得上 | 工序走完一半以上，证据相互印证 |
| 已修复 | 自己改了，或者确认别人改了 | 提交落地，或者复盘时确认已修 |

已修复要写明来源，是自己改的还是别人改的。两种来源复盘时归因完全不同。

## 常见错误

- 该对账的时候跳过，昨天有结论、缺陷单有新进展，却直接开新单
- 只看描述加搜几下代码就下确定结论
- 一次分析好几条，附件下漏
- 搜不到就当没有（看基本原则）
- 分析完不写文件，不记教训
