# 调试的基本原则

这一份是这个 skill 的核心。八条跟语言和项目类型都无关的调试原则，都是从真实工程里摔出来的。每条配一个真实例子，例子只做启发，实际工程不一定长这样。

## 1. 先分类，再定位

拿到 bug，第一反应别是搜代码。很多看起来像代码问题的事，根因在配置、数据、版本或归属层。先判断症状属于哪一类，显示、布局、逻辑、数据、资源、构建，再决定从哪下手。

真实例子。某个元素位置错的问题，先查布局和锚点参数，再查代码逻辑。结果确实是布局参数，一行代码都没改。

## 2. 下结论要证据互相印证

要说某层没问题，得几个证据同时指向这个结论，不能看一个现象就下判断。单个现象容易骗人，看着像 A，根因其实是 B。做法是先列出如果真是这层的问题应该看到什么，一个个验证，全对得上才敢排除。

真实例子。某次黑屏，单看屏幕看不出是哪层的事。最后靠四个证据，进程在不在跑、启动日志正不正常、有没有被暂停、负载正不正常，四个都正常，才敢说问题在显示合成层，不是渲染层。

## 3. 卡顿先数时间间隔

卡顿、延迟、抖动这类问题，先做定量分析，数时间间隔、频率、数值，再谈根因。别上来就猜性能和动画。定性判断没法定位问题环节，一个数能指向上游。做法是定位问题时间点，逐条记关键事件的时间戳，算间隔找异常值，再定位异常环节。

真实例子。某次操作卡顿，本地复现不了，最后逐条统计消息间隔，发现某个位置的上报延迟了快一倍，结论是数据源延迟，不是本地渲染。

## 4. 先弄清是谁的问题，再进仓库

先确认症状属于哪个进程、模块、界面、仓库，再进对应仓库查代码。别默认归到自己熟悉的仓库。一个界面可能是好几个工程一起渲染的，进错仓库就是在错误的地方找不存在的东西。做法是先看附件确认是哪个应用哪个界面，再确认它由哪个仓库负责，最后才进仓。

真实例子。某次界面显示异常，视频里先后出现好几个应用，问题在最后一个里。第一次在错误的工程里查，全错。

## 5. 先看是不是已经被人修了

深入分析之前，先进仓 pull 最新代码，再看最近几天的提交，确认目标文件有没有被改过。多人高频改的文件很可能已经被人修了。在旧代码上推根因是白费功夫，还可能把已经修好的误判成还要修。做法是进仓先 pull，再看 git log，目标文件在不在近期提交里，据此判断是已修待验证，还是仍然要修。

真实例子。某个问题定位到配置文件的一行，其实修复提交几天前就合入了。先 pull 再看提交，能立刻发现已经修了，不用重推一遍根因。

## 6. 搜不到不等于没有

搜关键词一个都不中，不代表代码不存在。可能是配置映射、版本开关、命名差异、子模块把它藏起来了。直接判不在本仓库是最省事的逃避，也最容易错。做法是搜不到就追映射、配置、版本这条链，目标可能通过某个映射指到了另一个子应用或仓库。

真实例子。某个功能搜个性化一个都不中，判代码不在本仓库。其实是一个配置开关把它指到了另一个子应用，代码就在本仓库里。

## 7. 别人说的结论要自己验证

AI 报告、别人说的已转某处处理、评论里的结论，都是二手信息，要自己验证过才能信。二手结论的判断逻辑不一定适用于实际场景，比如它不知道某个渲染其实投射到了别的屏。做法是把二手结论当线索，不当结论，动手验证代码和运行证据后再决定信不信。

真实例子。某次问题，一份 AI 报告判不是本层的事，因为报告按进程名做归属，不知道某个渲染会投射到别的屏幕。自己验证代码后推翻。

## 8. 证据不够就不下结论

检查动作没做够，只许标无法定论或信息不足，不许标确定结论。这是防止浮躁的深度，免得每条都写结论，一半检查动作却根本没做。做法是每条 bug 附打点表，工序不过关，结论等级就上不去。

真实例子。一次批量分析声称达成率很高，打点表一查，大部分只做了读描述和搜代码，运行证据、附件、复现几乎没做。那些结论都是猜测。
