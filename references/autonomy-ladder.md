# 修复和提交，分四级

默认只读，级别越高越谨慎。级别定在哪，写在 `project-config.md` 的 autonomy 字段里。升到更高的级别，要先征得使用者同意。

## L0 只读

分析 bug，给根因和修法，不动代码。

- 允许。读代码、读日志、跑搜索、看 diff。
- 禁止。改文件、提交、推送。

## L1 提议

在 L0 基础上，把修复方案写成明确的改动清单，等用户确认。

- 允许。给出改动文件、改动点、改动理由。
- 禁止。在用户确认前改任何文件。

## L2 自动改

用户确认方案后，直接改代码，不提交。

- 允许。按确认过的方案改文件，跑测试，给用户看 diff。
- 禁止。改方案之外的东西，提交，推送。

## L3 自动提交

改完直接提交推送，走代码审查。

- 允许。git add、commit、push，按提交验证铁律确认成功。
- 禁止。改方案之外的东西，绕过审查，强推。

## 回退

每一级都留退路。L2 改坏了，git checkout 还原。L3 提交错了，推送前能改，推送后走审查页面撤销。改之前先确认当前分支干净，别把别人未提交的改动卷进来。

## 提交验证铁律

提交推送之后，只看 exit code 会骗人。远程拒绝的推送也可能返回 0。

1. 检查输出里有没有 SUCCESS 关键字。
2. 检查有没有生成审查链接。
3. 检查有没有 new reference 或 new branch 之类的确认信息。
4. 输出里出现 rejected，直接当失败处理。

四项按 `scripts/git_push_verify.py` 自动跑，脚本把检查写死了，不靠肉眼。

## 提交常见坑

- 分支名写错。推送前用 git rev-parse --abbrev-ref HEAD 确认分支名，再对照远程分支全名。
- 提交信息开头被 BOM 字符污染。报错说格式不对，先检查首行有没有隐藏字符，用 git commit --amend 重提。
- 提交信息格式不符。第一行必须以规定的类型开头，规定的字段必须填。
- 子模块分支名。子模块的远程分支名要和远程仓库一致，别自己猜。
