# 复盘怎么复盘

复盘要找的是自己为什么没对，再把教训变成下次能用的规则。价值在第三个问题。

## 每条给过结论的 bug 都要写三部分

### 1. 昨天我的结论是什么

写下昨天对这条 bug 的判断。根因方向、归属判断、建议的下一步。比如，我判断是渲染逻辑的问题，不是配置问题，建议改某处代码。

### 2. 人类后来做了什么

去缺陷系统看后续进展。开发、测试、其他团队改了什么，转给了谁，最终根因是什么。

### 3. 我为什么没能得出正确结论

这部分最容易跳过，也最重要。连问三句。

- 人类是用什么方法得出正确结论的。看日志、对比版本、本地复现，还是查提交。
- 我为什么没用同样的方法。是不知道有这个方法，那就补进基本原则，还是知道但没做，那就靠打点表强制。
- 如果当时做了这个动作，结论会有什么不同。

只写方向对、方向偏，不回答为什么没做对，等于没复盘。找不到原因往往不是没能力，是没执行。这一步不深挖，下次还会犯。

## 复盘完要更新经验库

把第三问的答案写成一条能复用的教训，记进 `lessons.md` 的偏差表。

| 字段 | 说明 |
|------|------|
| 业务模块 | 这条 bug 属于哪个业务模块，比如订单、支付、登录 |
| 偏差类型 | 比如代码逻辑看成配置问题，性能猜测看成数据时序 |
| 示例 | 这条 bug 的匿名编号 |
| 教训 | 一句话，下次能直接套用 |
| 分类 | 属于哪一类症状，显示、逻辑、数据、资源 |
| 验证路径 | 正确做法是什么，根因只是其中一半 |

## 什么时候复盘

每天开始分析前，复盘昨天的。下班前再查一次，新评论可能一天里任何时候出现，只看一次容易漏。

## 铁律

- 复盘没做完，不许开始今天的新单。
- 只写对错、不写为什么没做对，等于没复盘。
