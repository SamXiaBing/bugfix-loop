# 证据够不够，检查一下

## 为什么要有这道检查

分析 bug 最常见的失败不是判断错，是判断太快。只看描述，搜两下代码，就敢写确定结论。这道检查用一条硬规则拦住这种习惯，适用的检查动作至少做一半，这是工序保底，等级另看证据。

## 检查动作（九项）

| 编号 | 动作 | 说明 | 什么时候算数 |
|------|------|------|-------------|
| 1 | 读描述和评论 | 把缺陷单正文和全部评论读完，不漏上下文 | 必做 |
| 2 | 看附件 | 截图、视频、复现步骤，能看就看 | 有附件时 |
| 3 | 拿运行证据 | 日志、控制台、事件流、错误上报，定位问题时间点，看实际行为 | 有运行证据时 |
| 4 | 搜代码 | 找到关键逻辑或配置在哪 | 必做 |
| 5 | 读代码 | 读到具体文件具体行，搜到不算完 | 必做 |
| 6 | 查最近提交 | git pull，再看 git log 最近几天的提交，确认有没有人已经修了 | 必做 |
| 7 | 确认归谁管 | 症状属于哪个进程、模块、仓库、界面，别默认归自己 | 必做 |
| 8 | 复现 | 在本地或编辑环境试着复现 | 复现得了时 |
| 9 | 确认数据真的到了 | 数据、信号、请求有没有真的到达，别假设到了 | 涉及交互和状态时 |

## 怎么判定

算一下可做的项数，再算做完的项数。做完多少只说明工序走没走完，等级另看证据。

- 工序。适用的检查动作至少做一半，这是保底，防的是只做一两项就敢下结论。
- 等级。等级看证据撑不撑得住。少数动作给出相互印证的硬证据，够自信也能下确定结论；动作全做但证据互相矛盾，一样下不了。
- 信息不足。关键证据拿不到，运行证据没有、复现不了，写信息不足。拿不到要分清，列表里真没有，还是没下载成，后者先去补拿。
- 矛盾。做完的够了但证据互相矛盾，继续查，不许硬写结论。

## 这道检查从哪来

有一次批量分析八条 bug，报告说完成率 87.5%。把检查动作列出来一数，读描述评论八条都做了，搜代码六条，读代码只有两条，拿运行证据一条都没有，看附件一条都没有。大部分 bug 其实只做了读描述和搜代码两项，远远不到一半。那些确定结论都是基于二手信息的猜测。这道检查就是把这种浮躁的深度抓出来。

## 落地要求

每一条 bug 的当天报告里都要附上九项检查动作，各自标做没做、适不适用，再写一句备注。这张表是结论可信度的证据，不是走过场。
